# 归位保持与相机对照

当前修改：GUI 的两次 go_home(1, wait=True) 成功返回后，仅读取反馈并继续故障/看门狗检查，不再调用 hold_current、set_joint_positions 或 set_gripper_pos。页面显示“保留 SDK 归位目标”。由于没有读取到 SDK 内部目标，hold_target_rad 为 null，反馈不伪装成目标。

归位后的再次暂停、页面失联维持原目标。运动中暂停和 VLA 正常结束仍捕获当前位置保持。故障和紧急停止路径未放宽。

80 项离线测试及前端构建通过；尚未执行本次真机对照，不能认定抖动已解决。

## 之后在现场执行的对照

1. 相机断开，不执行 VLA。在操作者确认路径畅通后连接机械臂、双臂归位，确认出现“保留 SDK 归位目标”。观察约 15 秒，记录抖动和声音。
2. 保持同一姿态，不再归位、不切换模式，点击连接相机，观察约 15 秒。
3. 点击断开相机，维持同一 SDK 目标，观察约 15 秒。必要时重复开/关以确认现象可复现。

如果第一阶段已经持续抖动，不必继续叠加相机负载；记录该现象并进一步核对 SDK 控制线程、负载模型和控制器参数。出现异常应由现场操作者及时停止测试。

日志位置：client/logs/gui-*.jsonl。归位事件 target_update 应为 unchanged、hold_source 为 sdk_home；重复暂停不应出现新目标。现有 tick_gap_max_ms 是上层反馈检查间隔，不等于 SDK 电机线程周期，不能单独据此确认底层抖动原因。反馈幅度与声音仍需现场观察或进一步采样。

## 相机进程隔离版本

现场反馈：相机断开归位后不抖，连接相机后抖动。日志三次相机连接分别出现约 460、451、435 ms 的上层反馈检查间隔；此前约 40 ms。JPEG 编码约 1.5–2 ms。此结果支持优先检查相机初始化/采集与 SDK 共进程竞争，但不是底层 SDK 线程延迟或 GIL 根因的直接证明。

GUI 已改用 camera_process.CameraProcess，通过 spawn 启动新进程，避免 fork 继承 SDK/CAN 控制资源。RealSense 初始化、图像读取和 JPEG 编码都在子进程内执行；相机进程只接收相机配置，不创建机械臂实例。相机失败停止读取，机械臂健康时保留原有保持。演示模式和命令行 client.py 相机路径未改动。

82 项离线测试通过，含真实子进程的合成图像读取/编码、子进程故障后保持验证。没有执行本次真实相机或机械臂复测。现场仍按上面的关→开→关步骤验证；新相机连接事件应包含 camera_backend=separate_process 和 camera_pid。若仍抖动，继续检查系统调度、USB/CAN 接口与供电等进程隔离不能排除的因素，不自动增加平滑或放宽保护。
